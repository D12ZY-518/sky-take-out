2026-09-28 增加了禾巷视觉层：商家登录/管理页由 `frontend/admin-theme.css` 覆盖旧构建包的视觉，适配器在响应时注入样式；新工单页和浏览器版 Agent 页直接使用相同的深绿、米白配色与服务流程说明。小程序点餐首页、个人中心、帮助页和 Agent 页也做了配色、圆角、标题层次调整；原来的点餐列表与交互结构仍在。这里的改动不能证明整套前端为原创，尤其小程序是编译包样式覆盖，未来重新编译源码可能丢失覆盖，需要迁移到真正的 UniApp 源码。

## 后台管理端（浏览器）

先启动本仓库的 Docker 服务，再用本地适配器服务旧后台构建产物；只监听 `127.0.0.1:8081`：

```powershell
node scripts/legacy_admin_demo.js 'D:\AAAAAAAAAA——developor\资料\day12\frontend-source\nginx-1.20.2\html\sky'
```

打开 `http://127.0.0.1:8081/`。适配器把旧页面的 `/api/*` 转发到当前 Java 的 `/admin/*`；不修改旧构建文件。商家侧栏底部另有“售后工单”入口，打开本仓库新增的工单处理页；它不是顾客聊天入口。只对本机演示，不要直接暴露公网。停止时在运行该命令的终端按 Ctrl+C。

品牌改名由本仓库适配器完成：旧包原件不变，响应时替换旧标题/可见品牌字样，并用本仓库的 SVG 标识覆盖旧 Logo 请求。修改适配器后若 8081 仍显示旧名，请重启这个 Node 服务；Java/Python 容器里的标题和 Agent 自称也需重建镜像后才会变为新名。

2026-09-27 浏览器验收：工作台、菜品、分类、订单列表与详情、套餐空状态、数据统计、员工列表均可打开；菜品 OSS 图片可见。适配器只为旧包转换 Java 的日期数组，重写其过时的 WebSocket 地址，并在订单详情里停止展示旧包硬编码的 6 元配送费。Java 新增 `/admin/order/details/{id}`，沿用管理员 JWT，不放开用户端订单归属校验。旧演示卷中已确认的种子乱码用 `docker/seed/repair-demo-names.sql` 按主键和原十六进制值修复，旧资料原件未改。

工单页 `http://127.0.0.1:8081/service-tickets.html` 调用 `/admin/tickets`；可筛选、分页，状态仅按“待处理→处理中→已完结”推进，相同状态重试不会重复变更。未登录读工单返回 HTTP 401。已用一条明确标记“联调测试”的工单验收两个状态动作，现保留为“已完结”样例，不是真实售后诉求，也不代表已退款。Java 单元测试 35 项通过，旧包适配脚本自检通过。

边界：旧包没有原始可维护的 Vue 工程，兼容改写依赖当前构建产物的固定字符串；升级旧包需重新核对。WebSocket 当前仅用于本地订单提醒演示，未做生产级认证和部署审计。商家端写操作（改菜、改套餐、接单、退款等）未逐项实测；旧库还存在一个分类 ID 200 缺失的“小小汉堡”历史记录，且价格异常，未擅自删除或改价。当前演示库套餐为 0 条，统计页近 7 日为 0 不等于统计接口故障。

## 顾客小程序（微信开发者工具）

导入 `frontend/mp-weixin/`。`project.config.json` 仍带旧资料中的 AppID；没有该 AppID 的权限时，应在微信开发者工具中切换到自己的测试 AppID。本地 HTTP 请求还需开发者工具允许不校验合法域名。默认首页仍是旧点餐页；顾客可以从“个人中心 → 帮助与客服 → 智能客服”进入，也可以从“订单详情 → 遇到问题”进入并自动带上订单号草稿。Agent 页调用 `http://localhost:8080/user/service/chat-python`，不是直接调用 Python，也不把内部令牌交给小程序。

**身份边界：**这个 Agent 页没有接入旧 UniApp 的 Vuex 登录令牌，在 Java 开发配置下以演示用户 1 运行；它不能证明真实微信登录、用户隔离或手机真机联网。`localhost` 在真机上指向手机本身，不能直连电脑服务。页面为每次发送生成 `requestId`，网络结果不明时保留同一 ID 供重试；这只是本地体验，真实写操作仍需人工核对结果。创建工单会写入本地 MySQL，聊天会调用付费模型。

2026-10-17 更新：网页和小程序依据结构化 `outcome` 判断是否结束待重试状态；`unknown`、缺失字段及 Java 降级都保留原 ID。点击重试先 GET `/user/service/ticket-result`：查到当前用户的原工单就展示原工单号，不重新调用模型；暂未查到才复用 ID 发送原消息，查询故障则不重发。网页/小程序真实脚本的无网络回归见 `node frontend/test_chat_retry.js`，不代表已在当前 Docker/真机上做真实丢包验收。此次需要同步更新 Java 和 Python，旧容器不会自动加载工作区源码。

旧小程序只有编译后的 JS/WXML，并无原始 UniApp `.vue` 页面。新增帮助页与 Agent 页是微信原生页面，而“我的”和订单详情入口直接接在旧编译产物中；若将来找到原始 UniApp 工程并重新编译，须将这些入口迁回源码，否则编译产物会覆盖它们。

## 2026-09-27 点餐首页联调修复

先前“休息中 + 菜单空白 + 无图”是三个独立原因，不是一个 OSS 故障：

1. Redis 中 `shop_status` 不存在，Java 将缺失值解释为停业 `0`。本次通过管理员接口将当前本地环境设为营业 `1`；这是运行状态，不随代码提交。重新创建 Redis 数据卷后，应通过后台重新设置，不能通过修改生产默认值强制开店。
2. 旧编译包首页把 `uni.login` 和头像授权并行启动，登录 code 可能尚未返回，分类请求又受用户 JWT 保护。已在 `common/vendor.js` 的旧首页逻辑中改为 `uni.login → /user/user/login → 保存 JWT → 请求分类与菜品`，不放开受保护的订单接口。修复发生在 UniApp 编译产物中；若重新编译原始 UniApp 工程，需要迁回源码。
3. 新 Docker 演示库原本只有 2 道 `image` 为空的菜。已从本机旧 MySQL **只读导出商品目录**，用 `docker/seed/03-legacy-catalog.sql` 追加 8 个分类、25 道带 OSS 地址的菜和 13 条有效口味；不导入旧库用户/订单，也不执行旧 SQL 中的 `DROP TABLE`。初始化新数据库时 Docker 会运行该脚本；现有数据库已单独执行一次。原种子中的空套餐分类已停用，两个无图演示菜保留并移到分类末尾。

验证：微信开发者工具取得的 `wx.login` code 经当前 Java 登录接口成功换到 JWT；带该 JWT 请求分类返回 `200`、9 个可用分类，第一类“蜀味烤鱼”返回 3 道菜；第一道菜的 OSS 图片从本机 GET 返回 `200 image/png`。2026-09-27 重启 Java 后，开发者工具模拟器中实际看到了“营业中”、首类 3 道菜及图片；手动点击第二类“蜀味牛蛙”后，页面切换为该类菜品并显示图片。开发者工具 Network 中登录、分类和菜品请求均为 `200`。这完成了**本地模拟器的菜单视觉与分类切换验收**，但不代表真机、支付、下单或售后聊天已经验收。真实微信用户与 Agent 演示用户 1 是不同身份，不能把二者订单混说。

本次联调还重新构建并重启了 Java 镜像，移除了用户和管理员 JWT 拦截器中输出完整令牌的日志。`mvn -pl sky-server -am test` 通过 27 项测试；新容器启动后，最近 200 行日志里没有旧的令牌日志字段。这里验证的是这两处日志语句及当前运行实例，不能据此推断所有日志都已完成敏感信息审计。

本地重启后若再次显示“休息中”，先检查 `GET /user/shop/status`，在管理端将店铺设为营业；若菜单仍空，再查小程序 Network 中 `/user/user/login`、`/user/category/list`、`/user/dish/list` 的响应，不要先去改 OSS 或关闭 JWT 鉴权。

## 面试时如何讲

旧点餐 UI、后台管理 UI 与当前售后 Agent 是三条不同体验路线。前端只发送消息、会话 ID 与同一次动作的请求 ID；Java 解析可信用户身份并转发 Python；Python 再通过受控工具回调 Java。此次前端接入证明的是本地演示路径，不能把旧小程序的演示用户 1 说成已打通真实微信身份链路。
