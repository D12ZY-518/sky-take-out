# 客服 Agent 第二轮排查 · 2026-10-21

继续首轮排查，仍只修改 Python 客服 Agent。未修改 Java、业务数据库、前端或运行镜像，未调用付费模型。

## 新确认并修复的四类问题

| 复现问题 | 当前处理 |
| --- | --- |
| 工单首次提交超时，同 requestId 再发 HTTP 请求却新建 Context；模型不再调用写工具时 unknown 被误报为 completed | 缓存当前用户同 requestId 的原输入和执行事实，串行同 ID 请求；写入未知一直保留到取得确认回执。完成响应直接复用，不重复调模型或追加历史 |
| 工具循环在产生下一次 tool_calls 后截断，未配对调用使后续同会话请求违反模型消息协议 | 下一轮开始前补齐中断工具回执，明确结果无法确认；保留已有真实回执，不恢复旧工具执行或重放旧建单 |
| 40 轮本地对话累积 80 条消息、120 个检查点和 240 份 blob 版本，随轮数持续增长 | 每轮结束后仅保留最新检查点及最近完整用户轮，释放旧 checkpoint、writes 和 blob；按闲置时间和会话数限制总量，活跃会话不淘汰 |
| 工单业务拒绝、403 或建单参数错误只返回自然语言，模型仍可编造登记成功或订单详情 | Context 记录可信拒绝事实，HTTP 最终答复据此覆盖模型文案；真实工单回执和 unknown 的优先级高于普通拒绝 |

测试还覆盖纯读模型异常后同 ID 重试可以恢复 completed；只有实际未知写入才保留工单 unknown，不把所有失败都永久锁成未知。

## 容量与行为

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| AGENT_MEMORY_MAX_TURNS | 10 | 保留最近 10 个完整用户轮，包含其工具调用与回执 |
| AGENT_MEMORY_TTL_SECONDS | 1800 | 闲置 30 分钟的会话在后续请求时清理 |
| AGENT_MEMORY_MAX_SESSIONS | 1000 | 超额淘汰非活跃的最久未使用会话；全部活跃则拒绝新会话 |
| REQUEST_CACHE_TTL_SECONDS | 600 | 同 ID 请求的输入、执行事实与响应闲置保留 10 分钟 |
| REQUEST_CACHE_MAX_ENTRIES | 1000 | 保留未过期请求；满额时返回 unknown、请稍后重试，不驱逐仍有效的未知结果 |

相同 requestId 必须复用原始 message 和 sessionId，改动输入会被拒绝；不同用户即便 ID 相同也隔离。省略可选 requestId 时仅使用单次 Context，不占用跨 HTTP 重试缓存。

压缩通过公开 saver 接口读取最新检查点、重新保存全部当前 channel 值及 pending_writes；失败轮也压缩，防止反复失败积累检查点。测试确认并行工具部分失败时，已成功工单回执仍存在，恢复后没有第二次 HTTP 写入。保留完整用户轮以避免裁掉工具调用的一半。

## 仍需区分的限制

记忆和请求缓存仍在单进程内；进程重启、多实例或 TTL 之外不能靠此缓存保证恢复。跨请求持久去重仍依赖已有 Java/MySQL 唯一约束，用户端已有的原请求工单核对流程仍然必要。

历史压缩保留当前状态，放弃旧检查点回放和分叉，也不支持嵌套子图。本项目使用单层客服图。容量按轮数和会话数限制，没有实现 token 或字节级预算；过期清理由新请求触发。丢弃较早历史后，用户引用旧信息时可能需要重新查询或补充订单号。

本轮防止了已复现的拒绝结果被改写，不构成通用语义校验器，也没有穷尽全部幻觉场景。整轮总耗时上限、多进程持久化、真实模型全量评测和镜像更新仍未实现或验收。
