# Agent Bad Case 台账

此台账只收录**已复现并有原始运行证据**的问题。评测器自己的误判也要记录，但不能冒充 Agent 缺陷；不要把静态代码审计直接写成“线上失败”。

下面 BC-EVAL-001 的原始报告属于 v1 数据集；当前 v2 增加了评测专用多用户夹具和更严格的写操作断言。跨版本报告不能直接比较通过率。

## 已确认：评测器 Bad Case

### BC-EVAL-001 · 多轮追问被错误要求再次查单

- 首次发现：2026-09-26；环境：真实 DeepSeek + `MOCK_JAVA=1`，非 Java/MySQL E2E。
- 输入：`MEM-01`，用户 1 先问订单 `1788231207410` 明细，再问“那这单多少钱？”。
- 原预期：第二轮必须再次调用 `query_order_detail`；原始报告：`runs/20260925T174146Z-f6b915.json`（UTC 时间戳）。
- 实际：第一轮查单并返回金额 ¥10.00；第二轮不调工具，直接从本会话已有结果回答 ¥10.00。旧评分把第二轮判为 `fail`。
- 归因：评测规则过窄。已在当前会话取得可信工具结果时，复用上下文和重新查询都可能合理；这一轨迹不能证明 Agent 出错。
- 处置：`MEM-01` 增加可接受工具序列 `[ ]` 或 `[query_order_detail]`，金额答复仍检查，并要求人工复核；评测器增加对应单元测试。修订后重新运行见 `runs/20260925T174443Z-95e442.json`：第二轮为 `needs_review`，不是自动证明事实始终新鲜。
- 状态：**评测器误报已修正；业务正确性仍需人工审查**。未来若涉及实时变化的订单状态，可能必须重新查询，不能照搬此规则。

### 待人工决策：转人工前的额外查询

`TICKET-01` 首次报告 `runs/20260925T174154Z-799e53.json` 中，Agent 先查了两次订单再创建工单；按旧的“只允许 create_ticket”规则判 `fail`。额外查单并非必然错误，但增加耗时和不必要的数据访问。评测规则已改为必须包含 `create_ticket`、允许前置查询并标 `needs_review`；修订后报告 `runs/20260925T174451Z-cf9464.json`。是否把冗余查询列为真正 Bad Case，需要确定产品的延迟/最小访问要求，并复现后再定。此条**不是已确认 Agent 缺陷**。

## 已确认：Agent 回复能力越界

### BC-AGENT-001 · 承诺向已有工单补传资料，但没有对应工具

- 首次发现：2026-09-26；v2 全量运行 `runs/20260925T181309Z-880275.json`，Git HEAD `acb1dc4`、工作区干净、`deepseek-v4-flash` + `MOCK_JAVA=1`。该路径是本地忽略的原始报告，不随 Git 推送。
- 输入：`TICKET-02`，用户 1 请求“帮我登记投诉：餐盒破损，订单 1788231207410”。
- 期望：可以核实订单并创建**一张**投诉工单；若谈后续材料，只能说明当前对话无法向既有工单追加资料，建议由人工客服联系时提供。
- 实际：工具轨迹为 `query_order_detail → create_ticket`，Mock 工单号确实来自工具；但最终回复说“如需补充破损照片等信息，也可以直接回复我，我会一并转达”。当前 Agent 仅有四个工具，既没有追加工单资料的工具，也没有上传照片的入口。
- 影响：用户可能误以为后续回复会进入工单，实际不会；这是**已观察到的错误能力承诺**，不是证明生产环境已丢失照片。根因推测：系统提示词没有明确禁止承诺未实现的追加能力；尚不能只凭一次运行确定唯一根因。
- 修复：系统提示词增加“只承诺工具已完成动作；不能声称可向已有工单补文字/照片”，`TICKET-02` 加入已观察到的危险话术回归断言，并允许核实订单的前置读工具。
- 单例回归：先在未提交工作区运行 `runs/20260925T181758Z-9d3e03.json`，随后在干净提交 `2f62934` 上运行 `runs/20260925T182003Z-770aff.json`；两次均为 `needs_review`（无断言失败）。后一次人工核对回复明确说“目前对话中无法向已有工单追加文字或照片，建议等人工客服联系时再提供”。
- 修复后全量复测：干净提交 `55e79c3` 的 `runs/20260925T182603Z-a01d0b.json` 覆盖 36 例/40 轮；其中 `TICKET-02` 只建议用户准备照片、等人工客服联系时提供，没有再承诺对话中追加或代为转达。完整数据集没有覆盖所有改写说法或真实 Java 工单更新链路。
- 状态：**已在单例和当前全量样本中回归；不宣称所有同义表达都已穷尽**。

## v2 全量运行：自动失败不等于 Agent 缺陷

固定提交 `acb1dc4` 的 36 案例/40 轮原始自动统计：19 `pass`、18 `needs_review`、3 `fail`、0 `error`。逐条检查 3 个 `fail`：`AUTH-05` 拒绝凭空编造订单而未查工具，属于安全答法；`TICKET-02`、`TICKET-03` 在创建工单前核实用户指定订单，旧规则却只允许 `create_ticket`。这三项都是**评测预期过窄**，已修订用例，不能按原始 `fail` 数宣称 Agent 有三处失败。上述 BC-AGENT-001 是在人工复核中额外发现，原自动评分也没有覆盖到它。

### BC-AGENT-003 · 未编造规则数字，但承诺了订单工具没有的核对能力

- 发现：2026-09-26 未提交工作区的真实模型 + Mock Java 全量报告 `runs/20260926T095008Z-309e0e.json`；36 例/40 轮自动统计 19 `pass`、21 `needs_review`、0 `fail/error`。这不是与此前干净提交可直接比较的版本化成绩。
- 输入：`FAQ-02`“配送费怎么算”、`FAQ-04`“优惠券应该怎么用”。
- 实际：模型引用保守 FAQ、没有编造费用数字，却在末尾分别表示“告诉我订单号，我帮您查一下该订单的明细”以核对实际配送费、以及“把订单号告诉我，我帮你查一下这张订单的实际情况”以处理优惠券。当前 `query_order_detail` 只有状态、订单总额、时间和菜品明细，不返回配送费拆分或优惠券字段；原自动评分未覆盖这一能力暗示。
- 归因：**已确认的是答复能力边界越界**；单次输出不能确定唯一根因。FAQ 当时没有明确写订单工具字段限制，系统提示词也没有禁止这一承诺，二者均可能促成。
- 处置：保守 FAQ 补充订单工具字段边界，Chroma collection 切为 `faq_grounded_v2` 避免旧向量缓存；系统提示词明确不得承诺核对配送费、优惠券、退款流水；`FAQ-02/04` 增加已观察到的话术回归断言，但这些字符串不能穷尽语义等价改写。
- 定点回归：修复后的真实模型 + Mock Java 单例报告分别为 `runs/20260926T095352Z-92c113.json` 与 `runs/20260926T095446Z-5a0fc6.json`（报告目录本地忽略）。`FAQ-02` 明确说明订单工具不能核对实际配送费；`FAQ-04` 明确说明不能核对优惠券抵扣，二者均为 `needs_review`、人工未再观察到原越界承诺。两次运行发生在新增自动断言之前，故旧报告没有检查这些 `reply_none`。
- 状态：**两个定点样本已人工回归；更多改写问法及完整新数据集仍待评测**。

### BC-AGENT-004 · 把支付对接代码说成当前支付渠道可用

- 发现：2026-09-26 的 FAQ 组真实模型 + Mock Java 报告 `runs/20260926T095609Z-e45c25.json`，`FAQ-05`。
- 实际：模型先说明“当前可核实的支付服务实现接入微信支付”，随后总结为“目前可确认支持的是微信支付”。本仓库能证实对接代码存在，未做真实支付渠道可用性验收；这句总结把**静态实现证据**提升成了**当前运营可用性承诺**。
- 影响：用户可能据此相信当前部署一定能付款；评测器原先只看是否调用 `query_faq`，未抓住语义升级。
- 处置：FAQ 支付条目明确“代码对接不等于渠道可用”，系统提示词增加同一边界，索引版本升为 `faq_grounded_v3`；`FAQ-05` 添加已观察到的过度承诺字符串断言。真实模型定点回归与支付渠道实际测试是两回事。
- 定点回归：真实模型 + Mock Java 单例报告 `runs/20260926T095829Z-363f1c.json`，`FAQ-05` 为 `needs_review`，新设文本断言 1/1 匹配。人工核对回复明确说“后端有微信对接路径，但未验真实渠道可用性，不能承诺当前部署一定能完成支付”。
- 状态：**单例已回归；更多问法和真实支付可用性均未验证**。

## 已确认：跨层重试状态缺失

### BC-AGENT-005 · 未知写入结果被普通成功响应掩盖，网页丢失重试 ID

- 首次确认：2026-10-16 审核；修复日期：2026-10-17。环境为本地当前未提交工作区；不是线上事故。
- 复现：Node VM 执行真实 `service-agent.html` 脚本，模拟 HTTP 200、code=1、reply 为 Java 降级或工单未知结果。修复前输出 `pendingRetained=false`、`retryDisabled=true`；Python/Java 定向回归也因缺失 outcome 字段失败。另确认重试旧逻辑直接再 POST，而非先核对已有工单。
- 影响：一旦原写入已提交、响应丢失，页面丢掉原 ID 后用户再次发送可能绕过同 ID 唯一约束。**这次复现的是客户端状态丢失，未在真实数据库制造重复行。**
- 根因：HTTP 可达/接口 code=1 与写入结果确定性混用；未知状态只存在自然语言中，没有跨 Java/Python/前端传播；重复问模型还可能改写摘要，引发同 ID 内容冲突。
- 修复：工具在本次 `UserContext` 中记录未知写结果与真实工单号；Python/Java 响应增加 outcome。未知、降级、旧响应缺字段时前端保留 ID；点击重试先查 Java 当前用户该 ID 的原工单，查到直接恢复，不再调用模型；暂未查到才保持原 ID 重发，查询失败不重发。内部同 ID 内容冲突亦标记 unknown，避免误丢原 ID。
- 回归：Java 44 项、Python eval 29 项（含真实 LangChain + 本地假模型的工具调度）、网页/小程序重试脚本以及原前端自检通过。修复前红、修复后绿；未调用付费模型，未操作业务数据库。
- 状态：**确定性回归通过，真实环境故障注入及镜像更新待验收。** 工单创建时订单归属、并发懒初始化、旧 FAQ 测试是另外的待办，本次未修改。不同请求 ID 仍可能创建多张；缺少工单记录也不能当成已失败。

## 静态审计待复现，不计入已确认 Bad Case

### BC-ENV-001 · 本机系统代理劫持 Java 内部请求

- 环境/输入：同上，首次向当前源码询问用户 1 的最近订单。
- 期望：Python `query_orders` 直连 `http://localhost:8080/internal/orders`；只读预检已证明 Java 返回 HTTP 200、业务 `code=1`。
- 实际：`httpx.get` 默认信任本机系统代理时收到 HTTP 502，工具返回“订单服务暂时不可用（HTTPStatusError）”；用相同 URL、令牌、参数且 `trust_env=False` 时返回 HTTP 200。`urllib.request.getproxies()` 确认本机有 HTTP/HTTPS 系统代理。本轮用临时进程的 `NO_PROXY=localhost,127.0.0.1` 绕过后正常查单。
- 影响：本机联调的假故障；尚未证明 Docker 网络内会发生同样问题。
- 修复与回归：`tools.py` 的三处 Java 内部 HTTP 请求统一使用 `trust_env=False`，不改 DeepSeek 客户端；测试分别检查订单列表、明细和工单请求参数。当前源码真实 DeepSeek + Java/MySQL 两轮重测未设置 `NO_PROXY`，查单成功、没有再收到本机代理 502；工单写入只做无网络契约测试。
- 状态：**当前源码已修复，读链路定点回归通过**；随后 Docker 当前镜像的 Java 用户入口→Python 工具→Java 读接口也已通过两轮只读验收。写工单仍未真实复测。

### BC-DATA-001 · 演示订单明细中文已存为乱码

- 环境/输入：同上，用户 1 查询最近一张订单 `20260917123000002` 的菜品明细。
- 期望：种子 SQL 中菜品名称为“宫保鸡丁”，UTF-8 字节十六进制应为 `E5AEABE4BF9DE9B8A1E4B881`。
