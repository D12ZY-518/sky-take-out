# 套餐缓存审计与练习（2026-09-20）

## 范围与证据

本轮只读审计生产代码，新增学习文档并同步学习记录；没有修改业务实现、安装依赖、操作运行中数据库或推送提交。
依据为两个 SetmealController、SetmealServiceImpl、SetmealMapper.xml、RedisConfiguration、仓库内 application 配置与 Spring 官方文档。
未运行接口复现、真实 Redis TTL/命令检查或并发压测；下文区分源码事实、推导与建议。

## 1. 优先修复：查询条件与 key 不一致

用户端入口：`sky-server/src/main/java/com/sky/controller/user/SetmealController.java:25`。

```java
@Cacheable(cacheNames = "setmealCache", key = "#setmeal.categoryId")
public Result<List<Setmeal>> list(Setmeal setmeal)
```

语法说明：`@Cacheable` 是 Spring 缓存注解；`cacheNames` 选择缓存区域；`#setmeal.categoryId` 是 SpEL 表达式，读取方法参数 setmeal 的 categoryId 属性。这里的 `#` 不是 MyBatis `#{}` SQL 占位符。

源码事实：Controller 接受整个 Setmeal 对象，只覆盖 status=ENABLE，没有清空 name；Mapper 的 list SQL 同时使用 categoryId、name、status 作为筛选条件。缓存 key 却只有 categoryId，缓存的值是整个 `Result<List<Setmeal>>`。

逻辑推导（尚未进行 HTTP 复现）：

1. 缓存为空时，请求 `/user/setmeal/list?categoryId=10&name=双人`。
2. 数据库只返回该分类下名字包含“双人”的在售套餐，结果写入 `setmealCache::10`。
3. 随后请求 `/user/setmeal/list?categoryId=10`，本应返回全部在售套餐，却命中上次的筛选结果。
4. 反过来先缓存完整列表，再按名字请求，也会忽略名字筛选。

核心规则：**同一个 key 对应的请求必须拥有相同的结果语义。** 固定由后端设置的 status=ENABLE 不必单独进入 key；可变化且影响结果的 name 则必须处理。

建议：此入口既然用于按分类展示，就只接收必填 categoryId，由服务端创建查询对象并固定 status；若业务确实需要名字搜索，明确独立查询契约，再决定复合 key 或搜索结果不缓存。不要让请求直接绑定数据库实体而无意开放其他筛选字段。
缺失 categoryId 时，当前 key 表达式会得到 null，亦缺少明确的客户端参数错误契约。

## 2. 全区域清理仍然有成本

源码事实：管理端修改、删除、起停售均使用 `@CacheEvict(cacheNames="setmealCache", allEntries=true)`；新增按分类清理。

`allEntries=true` 表示清空 setmealCache 区域，不是清空整个 Redis，也不是只删除当前分类。
仓库未声明自定义 RedisCacheManager 或批量清理策略。Spring Data Redis 2.7 系列默认清理策略使用 KEYS+DEL。因此按默认配置运行时，注解仍可能触发全库 keyspace 扫描并删除匹配该缓存前缀的 key；需在运行环境确认实际 CacheManager 与配置覆盖。

建议：写操作收集受影响分类，在事务成功后精确失效。换分类仍需旧、新两个分类；批量删除先查分类再删记录。如果保留管理用全区域清理，再考虑 SCAN 策略。

## 3. 事务时序不能套用菜品旧结论

源码事实：套餐失效注解在 Controller 上，未设置 beforeInvocation=true。新增、编辑、删除的 Service 方法有 @Transactional。

在当前正常 Spring 代理调用链、没有更外层事务的前提下，时序是：

```text
Controller → Service 事务代理 → 执行数据库操作 → 提交事务
           ← Service 返回 ← Controller 返回 → 注解清理缓存
```

所以不能把套餐说成“在改数据库之前就删缓存”。但是失效规则放在 Controller，未来从其他入口直接调用 Service 时可能漏清理；目前搜索到的这四个写方法调用方只有管理端 Controller，不能把未来风险说成已有 Agent 调用漏清理。

建议：将写事务和失效职责放到服务层，明确提交后执行。保留 Spring Cache 时，可使用事务感知 CacheManager 的普通 evict 或显式 afterCommit 回调；不能仅把两个注解移到同一方法上，就默认代理执行顺序必然正确。Redis 删除失败也不应误称为 MySQL 回滚。

## 4. TTL 与迁移边界

源码事实：仓库未配置套餐缓存 TTL。默认 RedisCacheConfiguration 没有 key 过期时间；这是基于仓库配置和框架默认值的判断，未检查运行环境覆盖配置。

建议：第一小步先给套餐缓存设置固定、可配置的 TTL，保留注解方案以学习 Spring Cache。无需为了复制菜品随机 TTL 直接引入新框架或升级依赖。5 分钟、30～40 分钟是此前练习参数，不是压测得出的最佳值；真正取值取决于数据更新频率、可接受陈旧时间与数据库承载能力。

重要补正：此前菜品 TTL 修改只影响新写入的 key；已经存在且无 TTL 的 dish_* 缓存不会因部署新代码自动过期。上线验收应检查旧 key，并在确认环境和范围后制定 SCAN 分批过期/失效方案；本轮没有删除任何运行中缓存。

此前 19/19 指 Mockito/JUnit 等测试通过，不等于真实 MySQL/Redis 集成验收通过。手动触发事务回调测试也不能单独证明运行中 Spring 事务代理接线正确。

## 5. 两个项目如何分工

- 苍穹外卖：优先展示缓存键正确性、参数边界、事务后失效、TTL、失败场景和测试。保留 Spring Cache 与手写缓存的对比价值。
- 黑马点评：安排热点击穿复现、锁内二次检查、本地锁与多实例边界、Redis 锁原子获取/安全解锁、锁租约到期、Lua 和压测。
- 不应以“项目不同”作为不修 bug 的理由。分工只决定在哪里训练高级能力；当前缺陷仍要修复。尚无压测证明苍穹需要分布式锁。
- 补正锁的概念：唯一 token+Lua 可避免误删别人的锁，但如果业务执行超过锁 TTL，仍可能同时有两个重建者；并非只写安全解锁就严格保证单重建者。

## 6. 2026-09-22 实施结果：用户端查询契约收口

已修改 `sky-server/src/main/java/com/sky/controller/user/SetmealController.java`，并新增 `SetmealControllerTest`；未改管理端失效策略、套餐 TTL、Mapper 或运行中的 Redis 数据。

实现内容：

1. `list` 不再绑定完整 `Setmeal`，改为接收 `@RequestParam("categoryId") Long categoryId`。因此前端多传的 `name` 不再进入 SQL 查询条件。
2. 方法内拒绝 `null`、`0`、负数；非正数请求不会调用 `setmealService.list`。
3. 后端新建 `Setmeal query`，仅设置 `categoryId` 和 `StatusConstant.ENABLE`。于是同一个分类 ID 只对应“该分类全部在售套餐”这一种结果语义。
4. `@Cacheable` 改为 key `#categoryId`，并以 `condition="#categoryId != null && #categoryId > 0"` 限制只有正数 ID 可参与缓存。`condition` 只跳过缓存，方法内 `if` 才负责拒绝请求。

测试证据：执行根目录 `mvn test`，22 项通过；新增的 3 项覆盖 null/0/负数不查 Service、正数只按分类加起售条件查询、缓存 key 与 condition 的注解配置。

验证边界：这是 Mockito/JUnit 单元测试。没有启动 HTTP 服务验证缺少 `categoryId` 时 Spring 的 400 响应，没有连接真实 MySQL/Redis 验证缓存命中，也没有清理部署前可能存在的 `setmealCache` 旧缓存。旧缓存 key 与新 key 的格式相同，若旧数据曾由 `name` 查询写入，则部署后仍可能短暂被读到；上线前需要在确认环境后清理该缓存区域，或通过一次受控的管理端缓存清理完成迁移。

## 7. 后续小步与验收标准

练习：只改用户端套餐列表入口，让它明确表达“查询某分类的全部在售套餐”，先不改失效策略。

需要做到：只接收必填分类 ID；拒绝非正数；在服务端创建查询对象并指定起售状态；缓存 key 与查询范围一致。
后续测试至少覆盖：缺少/非法分类参数、携带额外 name 不污染完整列表、正常命中跳过查库、空列表命中跳过查库。
本轮已完成“查询契约收口”的代码与单元验证。下一步才是套餐 TTL、精确失效和真实 Redis/MySQL 联调；不能把本轮测试通过说成全部缓存问题已经解决。
