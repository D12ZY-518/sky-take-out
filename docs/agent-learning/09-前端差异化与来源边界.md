# 禾巷前端差异化：做了什么，没做什么

## 一句话结论

当前前端已能在本地展示与旧课程包不同的品牌视觉，并把售后 Agent、商家工单放进合理入口；但旧点餐/管理功能仍以课程构建产物为基础。改色、改名不能被当作“从零独立开发前端”。

## 改动和理由

| 页面 | 这次做的事 | 为什么这么放 |
| --- | --- | --- |
| 商家登录与管理端 | 独立的深绿/米白主题层、登录页品牌区、统一侧栏与按钮 | 让旧包与新增工单页视觉一致；旧包原件不改 |
| 商家工单页 | 诉求登记→人工处理→标记完结的三步提示 | 明确 Agent 负责收集信息，商家负责决定；“完结”不是“退款” |
| 顾客点餐首页 | 店铺头图改为品牌色，菜品价格/分类/结算主色统一 | 仍以点餐为首页主任务，不把售后聊天塞到首页主位 |
| 个人中心→帮助→Agent | 统一服务中心视觉，客服页提供示例问题与演示边界 | 售后入口在需要帮助时出现；能从订单详情带订单号进入 |

## 复现和验收

1. 启动 Java/Python/数据库后，再启动 `node scripts/legacy_admin_demo.js '旧后台构建包路径'`，打开 `http://127.0.0.1:8081/` 看商家端；工单页在 `/service-tickets.html`。
2. 浏览器版 Agent 页由 Java 静态资源 `sky-server/src/main/resources/static/service-agent.html` 提供。不要在未确认模型费用与演示数据库写入前点击“创建工单”。
3. 微信开发者工具导入 `frontend/mp-weixin/`，逐页检查点餐首页、个人中心、帮助页、Agent 页和订单详情入口。小程序使用编译产物，单元自检不能代替模拟器视觉复核。
4. 无网络自检：`node scripts/test_legacy_admin_demo.js` 与 `node frontend/test_mp_agent.js`。前者检查适配器的固定兼容逻辑和主题注入，后者检查导航与同请求 ID 重试；都不覆盖真实下单/售后流程。

## 面试时这样说

“点餐与传统管理端来自课程项目，我没有把它说成原创。我的扩展是 Java 与 Python Agent 的售后链路：从顾客消息、受控工具查订单、必要时建工单，到商家端人工处理。为演示这条链路，我把旧前端接入当前后端，并做了禾巷的视觉统一。兼容层依赖编译包，真正长期维护需要拿到源码并迁移这些改动。”

如果面试官追问“你独立做了什么”，应拿出 Java/Python 代码、测试、BadCase、幂等与权限边界讲设计取舍，而不是只展示改过的页面。若追问“为什么不全部重写前端”，回答是求职阶段优先投入后端/Agent 可靠性；但这是技术债，不能包装成已完成的新前端。
