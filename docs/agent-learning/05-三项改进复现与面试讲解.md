# 三项改进：自己能重跑、能讲清的证据卡

本文件记录 2026-09-26 工作区的实验，**不是发布承诺**。命令在 `sky-take-out` 仓库根目录运行；Docker 演示环境默认用户 1 有订单 `20260917123000002`，菜品为“宫保鸡丁”。先用 `docker compose ps` 确认服务运行；若更换数据卷，先核对实际订单再改脚本参数。不要在真实用户库上执行写入测试。

## 1. 两轮真实读链路：从 Java 用户入口到 MySQL

```powershell
docker compose exec -T python-agent python -m eval.real_chat_smoke --base-url http://java-app:8080 --expected-order 20260917123000002 --expected-dish 宫保鸡丁
```

脚本每次生成新的 `sessionId`，依次向 Java `/user/service/chat-python` 提问“最近订单”和“刚才最新那单的明细”。它检查 Java HTTP/业务码、第一轮调用 `query_orders` 并提到预期订单、第二轮调用 `query_order_detail` 并提到订单号/菜名，且第二轮 `toolCalls` 不含历史 `query_orders`。当前 Docker 镜像上的一次输出为：

```json
{"result":"pass","turns":2,"firstTools":["query_orders"],"secondTools":["query_order_detail"]}
```

证据边界：这是**真实 DeepSeek + Java→Python→Java/MySQL 的一个自动化只读样本**，会产生模型调用费用；真实模型有非确定性，偶发失败要看响应与工具日志，不可直接归因为代码回归。脚本提示只读，但 Agent 工具选择本身不是硬写保护，所以只在隔离演示环境运行。它没有覆盖生产 JWT、其他用户、写工单、故障注入或性能分位数。

面试口述：

> 我把原来手工的两轮查单验收做成脚本，每次用新会话，从 Java 用户入口进入，验证第一轮查列表、第二轮查明细和实际菜名，并检查第二轮工具轨迹没有混入历史。它验证的是一条真实跨语言读链路，不是 Agent 全量准确率。

## 2. 建工单超时歧义：数据库才是幂等裁判

原风险：Java 已提交工单但响应丢失，Python 只看到超时；若重新生成工单号并 INSERT，会出现两张工单。现在 `ServiceChatDTO.requestId → Python ChatReq → UserContext.request_id → create_ticket payload → TicketCreateDTO.requestId → customer_service_ticket.request_id` 逐层传递。`requestId` 对模型不可见；MySQL 对 `(user_id, request_id)` 加唯一索引。第一次 INSERT 成功返回随机工单号；重复请求若内容相同，Java 读取原工单号；若同 ID 改内容，返回冲突。

新空数据卷从 `sky-take-out.sql` 建表；已有演示卷需执行 [`20260926-ticket-idempotency.sql`](../../docker/migrations/20260926-ticket-idempotency.sql)。迁移会检查列和索引，重复执行不再添加。**先核对目标是本项目演示库**，不要把脚本直接用于生产。

在可丢弃的演示库，刻意创建一条测试工单：

```powershell
docker compose exec -T python-agent python -m eval.real_ticket_idempotency --confirm-write
```

本次实际结果：第一次与相同内容重试返回同一 `ticketNo`，同一 `requestId` 改内容返回业务冲突；数据库按该 `requestId` 查到恰好一行。测试记录的 `requestId=it-1a69c508a76c4e13a3131a8c1788570d`、`ticketNo=TK86dd7991e8e04192bb7367e0c62b28`；核对后仅删除了这条精确匹配的测试行，工单表回到 0 行。脚本本身**不自动清理**，再次运行会生成另一条测试工单。复现时先根据输出的 requestId 查询/记录确切 `id`、工单号和内容，再决定是否清理；不要用清空表或删除数据卷代替清理。

关键限制：如果客户端不传 `requestId`，Java 会为**每个新 HTTP 请求**生成不同 UUID，只保证该次 Agent 内多次调用工具可去重，不保证浏览器重发整条消息时去重。真正的客户端重试必须复用同一个 requestId；换内容复用同一个 ID 也会被拒绝。已验证的是顺序重试与冲突，不是实际网络丢包、并发竞态或完整模型写链路。真实退款动作没有接入这套幂等机制。

面试口述：

> 超时只能说明我没收到响应，不能推断数据库没写。我给一次用户发送动作一个稳定 requestId，让 Python 工具透传给 Java，再用 MySQL 的唯一约束做并发下的最终判定。重复且内容一致取回原工单号，内容不一致报冲突。演示库的真实重复 POST 已验证只留一行；但如果客户端重试时换了 ID，仍可能重复，所以不能说“所有重试都幂等”。

## 3. FAQ：召回正确不等于事实正确

旧 30 条演示 FAQ 中有 Apple Pay、会员积分、固定退款时限等未经当前后端证实的说法。对账记录见 [`04-FAQ能力对账与面试复盘.md`](04-FAQ能力对账与面试复盘.md)。当前默认读取 `faq_grounded.json` 的 13 条保守问答，Chroma 使用独立 `faq_grounded_v3`，旧索引不再服务但未被删除。检索失败时明确“无法核实”，不让模型凭印象编政策数字，也不把“有微信支付对接代码”说成“当前微信支付一定可用”。

```powershell
docker compose exec -T python-agent python -c "import config,faq_rag; print(config.FAQ_DATA_PATH,len(faq_rag._load_faqs()))"
```

当前结果：`faq_grounded.json 13`。另一次通过 Java 用户入口的真实模型抽样问“你们支持 Apple Pay 吗？”，`toolCalls=[query_faq]`，回复指出当前后端没有 Apple Pay 实现证据、不能承诺支持；这只是**一条样本**。若未来业务方给出正式支付政策，应更新带来源的 FAQ，并重新评测；当前不能把“仓库未找到”当成真实商家的最终政策。

面试口述：

> 我发现旧知识库虽然能被准确召回，但来源本身不可靠。比如旧 FAQ 写 Apple Pay，后端只看到微信支付对接代码，连真实渠道是否可用也没验。我把未核实规则从运行时索引隔离，保留审计样本，并对无法确认的规则明确说不知道。我的结论不是“模型绝不会幻觉”，而是切断了一个已知的错误事实源，后续仍要做业务审核和生成结果评测。
