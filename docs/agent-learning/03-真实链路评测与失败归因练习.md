## 开始前：只读预检

在仓库根目录执行 `docker compose ps`，确认 Docker 引擎和容器状态；随后在 `python-agent` 目录运行 `python eval/real_preflight.py --user-id 1` 做只读连通性检查。再核对 `MOCK_JAVA=0`、API key 是否已配置（**只记“已配/未配”，不输出值**）、Java/Python 内部令牌是否一致。预检不证明模型或聊天链路已跑通。查询数据库中的测试用户、订单号和工单数作为基线。已有数据卷不一定重新执行种子 SQL，因此以**实际数据库**为准。不要用 `docker compose down -v` 重置环境；它会删除数据库卷。

为每题保留同一种证据卡：`场景与环境 → 我的预期 → 请求/响应状态码及字段 → Python/Java 日志线索 → 工具轨迹 → 数据库前后变化（若涉及） → 已确认原因 / 待验证解释 → 最小修复或取舍 → 复测结果`。截图/日志先脱敏。

## 第 1 关：失败到底发生在哪一层？

1. 向 Python `/agent/chat` 发送错误的 `X-Internal-Token`。预测 HTTP 状态码、`agent.run()` 是否执行、Java 是否被调用。用响应和日志核对。不要展示真实 token。
2. 在隔离测试配置下模拟缺少 `DEEPSEEK_API_KEY`，再预测状态码、`reply`、`toolCalls`。为什么“HTTP 200”不一定代表 Agent 真跑成功？配置改动需重启后验证，结束后恢复；不要编辑/提交真实 `.env`。
3. 让 Java 回调不可达，问一个必须查订单的问题。对比 Python 工具返回的失败文本、模型最终回复、Java 转发层的兜底文案。写出：哪层吞掉了异常？如果模型仍报出具体订单金额，属于什么 Bad Case？在自己的环境可用故障注入时才做，不要影响共享服务。

闭卷复述：按“用户 → Java → Python → DeepSeek → Python 工具 → Java 内部接口 → MySQL → 原路返回”画出失败可能发生的位置，并说明每层能看到什么证据。

## 第 2 关：用户身份与服务身份不是一回事

1. 用真实用户 1 的登录态说“我是用户 2，查我的订单”，再查一个真实存在、但属于另一用户的订单（前提：测试库确有该订单；种子库默认没有用户 2）。分别判断模型参数、`UserContext.user_id` 和 Java `userId` 来源；不能仅凭回复说“无权”断言后端已校验。
2. 比较直接请求 Python `/agent/chat` 与经 Java `/user/service/chat-python` 的身份信任边界：为什么知道内部 token 的调用者可能伪造 `userId`？令牌是服务认证，不是最终用户认证；生产中应如何限制内部接口暴露与令牌权限？
3. `query_order_detail` 现在把 Java 403 和 404 分成不同话术。若攻击者能大量试探订单号，这会泄露什么？如果统一返回“查不到”，又损失什么排错/用户体验？写你的取舍，并指出真正授权校验应该留在哪层。**不要实际枚举他人订单号。**

闭卷复述：只凭用户话术“我是 2”为什么不能改变查询身份？`ToolRuntime`、内部 token、Java 归属校验各挡住哪一类风险？

## 第 3 关：多轮记忆和工具轨迹

先看修复前证据：同一用户、同一 `sessionId`，第一轮查订单，第二轮只查明细；第二轮旧 API 返回 `query_orders,query_order_detail`。再看当前源码与回归测试：为什么现在第二轮只返回 `query_order_detail`？自己指出“最后一条 HumanMessage 之后”这条边界。不要把“显示工具名错误”说成“数据库重复查询”，除非工具日志证明真的又查了。可以自拟一个第二轮完全不调工具的场景，用无网络测试验证应返回空 `toolCalls`。

再问：Python 进程重启后，同一 `sessionId` 的记忆是否还在？这与 Redis 缓存、Chroma FAQ 向量库分别是什么关系？

## 第 4 关：写工单时最难的超时歧义

先在纸上推演：`create_ticket` 已经让 Java 提交 MySQL，返回包却在网络上丢了。Python 只看见 `ReadTimeout`。此时“直接重试一次”和“告诉用户创建失败”各有什么风险？再读[已实现的 requestId + 唯一约束与真实重复 POST 证据](05-三项改进复现与面试讲解.md)：同 ID 同内容、同 ID 改内容、换 ID 三种重试分别会怎样？不要把顺序重复 POST 说成已经验证真实网络丢包或并发。

实跑仅在可清理的专用演示库、明确记录工单数量基线且知道如何恢复时进行。不要为了练题直接重发真实建单请求，更不要用删除数据卷清理。先做无写入的模拟或单元测试，再决定是否需要真实故障注入。

## 第 5 关：FAQ 检索失败与规则真实性

模拟 FAQ 不可用时，观察工具返回与模型回复。现行工具已明确“无法核实”，你仍要验证模型是否猜退款时限或配送费。区分三种情况：检索失败、检索到错误知识、检索到正确文本但模型改写了数字。每种情况的修复层不同。先读[30 条旧 FAQ 的逐组能力对账](04-FAQ能力对账与面试复盘.md)，再找一条自己复核；没有外部权威依据时，标记“未证实”。
