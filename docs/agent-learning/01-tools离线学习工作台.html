工具 1 / 查订单列表

query_orders()：从用户身份到订单文本

先看完整方法 · query_orders()
仓库 python-agent/tools.py 的源码快照，保留原注释；向下看逐段解释。

读完源码后，应能说出两条路径：MOCK_JAVA=1 时用本地数据；否则用 httpx.get 请求 Java。

  1. status 和 limit 是模型可填参数；runtime 由框架注入。uid 从 runtime.context.user_id 得到。
  2. Mock 分支：先按身份、再按状态、最后截取前 limit 条。rows[:limit] 是 Python 切片。
  3. 真实分支：组装 params；status is None 时不发 status；httpx.get(..., params=..., **_JAVA_HTTP_OPTIONS) 才是发往 Java 的 HTTP 请求。这里的 trust_env=False 让内部 Java 请求不走开发机系统代理，但不影响 DeepSeek 客户端。
  4. raise_for_status() 处理 HTTP 4xx/5xx；body.get("code") 处理 Java 业务码。两者不同。
  5. body.get("data") or [] 把 null/空值变为空列表；再把 Java 的 orderTime 映射成内部的 order_time，复用格式化函数。
  6. 网络或解析异常由本工具捕获，返回字符串给模型，不会自动变成外层 chat() 的兜底。
Java 类比：[o for o in rows if ...] 约等于 stream().filter(...).toList()；"\n".join(...) 约等于逐行格式化后用换行符连接。
面试边界：这个方法的 limit 没有在 Python 侧校验；Java 服务有兜底夹逼。不要把“模型不能修改 userId”扩大成“接口无论什么情况都绝对安全”：内部令牌泄露或 Java 身份链路有缺陷时仍有风险。

query_order_detail()：订单号可以由模型给，归属必须由 Java 判断

先看完整方法 · query_order_detail()
仓库 python-agent/tools.py 的源码快照；向下看归属校验与失败分支。

模型可从用户的话里提取订单号；真正允许查看与否，要靠 Java 用用户身份和订单归属判断。

  1. order_number 是模型参数；uid 仍来自 runtime.context.user_id。

  5. 成功时从 data["order"] 与 data["details"] 取订单和明细，再格式化。

工具 3 / 写操作

create_ticket()：模型提出诉求，Java 创建工单

先看完整方法 · create_ticket()
仓库 python-agent/tools.py 的源码快照；向下看成功与超时边界。

这是四个工具中会让 Java 写入业务数据库的工具。成功消息必须建立在 Java 成功返回的工单号上。

  1. 模型只填类别、诉求内容和可选订单号。user_id 与 request_id 都由运行时注入，模型不能填。
  2. 发给 Java 的 JSON 有 userId/category/content/orderNumber/requestId。同一用户一次发送动作复用同一个 requestId。
  3. Mock 只造演示工单号，不落库；不能把 Mock 结果当数据库幂等证据。
  4. 真实分支 httpx.post(..., json=payload)；Java 依赖 UNIQUE(user_id, request_id)，重复且内容一致时取回原工单号，内容不同则拒绝。
  5. 只有 HTTP 和业务码都成功，才读取 ticketNo 并宣称已创建。
  6. 超时后结果未知，不能说已创建，也不能断言失败；同一发送动作重试要复用原 requestId。
幂等边界：历史演示 MySQL 验证了同一 requestId 只留一条工单。2026-10-17 补上跨层恢复：网页/小程序依据 outcome 保留未知请求；重试先查原工单，找到后不再调用模型。查不到才沿用原 ID 重发；如果首请求仍在进行，重试仍可能遇到内容冲突，这时继续保留 ID 核对。不同 ID 仍可能创建另一张工单。

2026-10-17 · 超时之后，怎样找回结果？

旧问题发生在工具之外：Java 把 Python 故障包装成 HTTP 200 + code=1 的普通回复，网页就删掉原请求 ID。数据库唯一约束还在，但用户下一次发送会换一个 ID。修复必须让“结果是否确定”跨越每一层。

情形程序依据页面动作
模型正常完成，且写操作无未知结果outcome=completed结束本次待重试状态；不等于退款成功
工具写超时、模型异常、Java 降级或旧响应缺少状态outcome=unknown，或状态字段缺失保留原消息、sessionId、requestId
点击重试，Java 查到当前用户该 ID 的工单GET /user/service/ticket-result返回真实原工单号，不再跑模型
查询暂未发现记录原请求可能仍在处理中保持原 ID 重发；查询故障则不重发

UserContext 新增的 write_result_unknown 和 ticket_no 属于本次请求。工具把执行事实写进去，HTTP 层读取；它们不由模型填写，也不是 checkpointer 中的长期聊天记录。run() 仍返回 reply、tool_calls 两项，新增可选 context 参数用于共享本次结果。

同日第二轮 · 谁能决定工单关联哪张订单？

举例：当前登录用户是 1，用户或模型给出订单 X，而 X 属于用户 2。userId 没被篡改，并不能证明订单号合法。修复前，写工单直接保存 X；现在 Java 在新建前查询 X，确认 order.userId 与可信用户相同，否则拒绝且不调用 insert。

  1. 先检查用户 ID 合法，将订单号首尾空格去掉；null、空串和全空格统一为不关联订单。通用反馈可以没有订单号。
  2. 按 userId + requestId 查询已提交工单。相同类别、内容和规范化订单号才返回原号；同 ID 改载荷仍冲突。取回原结果不依赖当前订单是否还存在。
  3. 新请求若填写了订单号，必须查到本人订单。不存在、无归属或属于他人时统一说“未找到可关联的订单，请核对订单号。”，不能静默去掉订单号后继续建单。
  4. 校验通过后才 insert。前置查询无法排除两个并发请求都查不到的情况，所以数据库唯一约束仍保留，冲突后再查回同一个结果。

# tools.py —— Agent 的"手脚"：模型只能动嘴决策，真正干活的是这里的 4 个工具
#
# 【它在架构里的位置】
#   agent.py 装配 create_agent(tools=[这里的函数]) → 模型看中某个工具 →
#   LangChain 框架自动调用对应函数 → 函数返回的字符串被喂回模型 → 模型组织成人话。
#   分工铁律：Python 只做"模型决策 + 编排"，真正查库/落库在 Java /internal/**，
#   这里用 httpx 回调 Java（MOCK_JAVA=1 时走本地假数据，不依赖 Java 即可联调）。
#
# 【@tool 装饰器干了什么】（装饰器 = Java 注解 + APT 生成器的合体，运行期生效）
#   1. 读函数的 docstring → 变成给【模型】看的工具说明书（所以 docstring 必须写清
#      "做什么 + 参数含义 + 枚举值"，模型全靠它决定什么时候用、参数怎么填）；
#      没有 docstring 直接报 ValueError，框架强制你写。
#   2. 读函数签名（参数名/类型注解）→ 生成 JSON Schema 发给模型选参；
#      ⚠ runtime 参数会被框架排除在 Schema 外，模型根本不知道它的存在。
#   3. 原函数被包进 StructuredTool 对象（query_orders 变成"工具"不再是普通函数），
#      想在单元测试里直接调原始函数，用 query_orders.func(...)。
import time
from dataclasses import dataclass   # dataclass = 自动生成构造器/getter 的 Lombok @Data 平替

import httpx                        # Python 界最常用的 HTTP 客户端（类比 Java 的 HttpClient/OkHttp）
from langchain.tools import tool, ToolRuntime

import config as c                  # 导入配置模块（注意：c 是别名，本文件统一用 c.XXX 取值）
import faq_rag                       # RAG 检索模块（lazy import 已在 faq_rag 内部做了，这里只引模块名）

# ==================== 运行时上下文：防越权的核心机制 ====================
# 【为什么 userId 不能写进工具参数】
#   工具参数是模型填的，而模型会被用户消息影响——用户说"帮我查 user 2 的订单"，
#   模型就可能真填 user_id=2，越权。解法：参数里根本不出现 userId，
#   真实身份由我们自己的代码经 agent.invoke(context=UserContext(...)) 注入，
#   模型看不到也改不了（Java 对照：不能信前端传的 userId，要从登录态 token 里取）。
#
# 【数据流】main.py 收到请求里的 userId → agent.run() 包成 UserContext →
#   → LangChain 执行工具时把它塞进 runtime.context → 工具函数里 runtime.context.user_id 取出。
@dataclass
class UserContext:
    user_id: int   # 当前登录用户 id，由代码注入，模型不可见。必填字段（不写默认值=构造时必须传）
    request_id: str = ""  # 同一用户发送动作的幂等键，模型不可见；仅写工具使用
    # 仅属于本次请求的执行事实；工具写入、HTTP 层读取，不能由模型文案决定。
    write_result_unknown: bool = False
    ticket_no: str | None = None

# 订单状态码 → 中文（字典 = Java 的 Map.of(...)；含义与 Java Orders 实体常量保持一致）
STATUS_TEXT = {1: "待付款", 2: "待接单", 3: "已接单", 4: "派送中", 5: "已完成", 6: "已取消"}

# ==================== mock 假数据（来源：本地 sky_take_out 库 user_id=1 的真实订单） ====================
# 列表套字典：Python 里最常用的"轻量 DTO"写法，o["number"] 取值 = Java 的 map.get("number")
_MOCK_ORDERS = [
    {"number": "1788231207410", "user_id": 1, "status": 5, "amount": "10.00", "order_time": "2026-09-01 10:53:27"},
    {"number": "cancel_test_1", "user_id": 1, "status": 6, "amount": "10.00", "order_time": "2026-08-30 22:51:33"},
    {"number": "1787893545201", "user_id": 1, "status": 5, "amount": "10.00", "order_time": "2026-08-28 13:05:45"},
    {"number": "test123", "user_id": 1, "status": 6, "amount": "10.00", "order_time": "2026-08-28 13:02:34"},
    # user_id=4 的两单（1776845110793 / 1775410154429）【故意】不放进来：
    # user 1 去查它们时应当走"查不到/无权"分支，用于验收越权防护（Java 侧 404/403 同理）。
]

# 订单明细：key=订单号，value=该单的菜品行列表（字典 = Java 的 Map<String, List<Detail>>）
_MOCK_DETAILS = {
    "1788231207410": [{"name": "王老吉", "number": 1, "amount": "6.00"},
                      {"name": "北冰洋", "number": 1, "amount": "4.00"}],
    "1787893545201": [{"name": "王老吉", "number": 1, "amount": "6.00"},
                      {"name": "北冰洋", "number": 1, "amount": "4.00"}],

# ==================== 调 Java 内部接口的公共零件 ====================
_HEADERS = {"X-Internal-Token": c.INTERNAL_TOKEN}   # 服务间鉴权头，token 必须与 Java yml 一致，否则 401
_TIMEOUT = httpx.Timeout(10.0)                       # 连接+读取总超时：Agent 一轮可能多次回调 Java，不设超时会被慢请求拖死
# Java 内部服务地址应直连；开发机的系统代理曾把 localhost 请求转走并返回 502。
# 仅作用于这三个 Java 工具请求，不改变 DeepSeek 客户端的代理配置。
_JAVA_HTTP_OPTIONS = {"headers": _HEADERS, "timeout": _TIMEOUT, "trust_env": False}


def _find_mock_order(order_number: str) -> dict | None:
    """按订单号在 mock 列表里找单。
    语法点：生成器表达式 + next(…, None) ≈ Java 的 stream().filter(...).findFirst().orElse(null)；
    返回类型 `dict | None` 表示"找到返回字典，找不到返回 None"（= Java 的 Optional<Order>）。
    """
    return next((o for o in _MOCK_ORDERS if o["number"] == order_number), None)


def _format_order_line(o: dict) -> str:
    """把一条订单 dict 拼成一行文本。
    mock 分支和真实 Java 分支都会先把数据归一化成同一组 key，再走这里 ——
    这样格式化逻辑只写一份（等价 Java 里抽取的公共 render 方法）。
    f"..." 是 f 字符串：{o['number']} 会在运行时替换成变量值（= Java 的 String.format/文本块）。
    """
    return f"订单号：{o['number']}  状态：{STATUS_TEXT[o['status']]}  金额：¥{o['amount']}  下单时间：{o['order_time']}"


def _format_detail(order: dict, details: list[dict]) -> str:
    """拼订单主信息 + 明细列表。lines 是列表，最后 '\\n'.join(lines) = Java 的 String.join。
    函数名前的下划线 _ 是 Python 惯例：表示"内部私有"（语言不强制，约定俗成）。
    """
    lines = [_format_order_line(order), "明细："]
    for d in details:
        lines.append(f"· {d['name']} ×{d['number']}  ¥{d['amount']}")
    return "\n".join(lines)


# ==================== 工具 1：查订单列表 ====================
# 签名解读：
#   status: int | None = None   → 可空参数（= Java 的 Integer status），用户没指定状态就传 null
#   limit: int = 5              → 带默认值的参数
#   runtime: ToolRuntime[UserContext] = None → 框架注入的上下文，模型不可见（见文件头 @tool 说明）
#   -> str                      → 返回类型注解（Python 注解不强制，但 @tool 会用它生成参数 Schema）
@tool
def query_orders(status: int | None = None, limit: int = 5,
                 runtime: ToolRuntime[UserContext] = None) -> str:
    """查询【当前登录用户】自己的订单列表，按下单时间倒序。用于回答"我的订单到哪了/有哪些订单/订单状态"。
    Args:
        status: 订单状态筛选，不填=全部。1待付款 2待接单 3已接单 4派送中 5已完成 6已取消
        limit: 最多返回条数，默认 5
    """
    uid = runtime.context.user_id   # 真实用户身份只从注入的上下文拿，绝不来自模型参数（防越权第一闸）

    # ---------- 分支 A：mock 假数据，本地过滤/截断（MOCK_JAVA=1 时联调用） ----------
    if c.MOCK_JAVA:
        rows = [o for o in _MOCK_ORDERS if o["user_id"] == uid]
        if not rows:
            # 按注入身份过滤；默认演示数据只有 user 1，评测可装载多用户假数据。
            return "你当前没有任何订单。"
        if status is not None:
            rows = [o for o in rows if o["status"] == status]   # 列表推导 = stream().filter()，注意缩进层级
        rows = rows[:limit]                                      # 切片取前 limit 条（= subList(0, limit)）
        if not rows:
            return "没有符合条件的订单。"
        return "\n".join(_format_order_line(o) for o in rows)    # join(生成器) 逐行拼文本

    # ---------- 分支 B：真实调 Java /internal/orders（过滤/截断由 Java SQL 完成，Python 不做业务） ----------
    try:
        params = {"userId": uid, "limit": limit}
        if status is not None:
            params["status"] = status
        resp = httpx.get(f"{c.JAVA_BASE_URL}/internal/orders",
                         params=params, **_JAVA_HTTP_OPTIONS)
        resp.raise_for_status()          # 4xx/5xx 抛异常（= Java HttpClient 的响应码检查）
        body = resp.json()               # 响应体转字典（= Jackson 反序列化成 Map）
        if body.get("code") != 1:        # Java 统一返回体 code=1 才是业务成功
            return body.get("msg") or "订单查询失败，请稍后再试。"
        # 把 Java 的驼峰字段（orderTime）归一化成 mock 同款 key（order_time），
        # 之后复用同一套格式化 —— 两个数据源，一个出口
        rows = [{"number": x["number"], "status": x["status"],
                 "amount": x["amount"], "order_time": x["orderTime"]}
                for x in (body.get("data") or [])]
        if not rows:
            return "你当前没有符合条件的订单。"
        return "\n".join(_format_order_line(o) for o in rows)
    except Exception as e:
        # 网络抖动/Java 没起/超时：绝不让异常炸穿 Agent（炸穿=整个接口 500，用户看到白屏报错），
        # 而是给模型一句可转述的话，由模型礼貌转告用户。type(e).__name__ 取异常类名，如 ConnectError
        return f"订单服务暂时不可用（{type(e).__name__}），请稍后再试。"


# ==================== 工具 2：查单张订单明细（含归属校验） ====================
@tool
def query_order_detail(order_number: str,
                       runtime: ToolRuntime[UserContext] = None) -> str:
    """查询【当前登录用户】某一张订单的状态、金额与菜品明细。用户问"某单多少钱/里面有什么/具体情况"时使用。
    Args:
        order_number: 订单号，由用户消息或上文对话提供
    """
    uid = runtime.context.user_id

    # ---------- 分支 A：mock ----------
    if c.MOCK_JAVA:
        order = _find_mock_order(order_number)
        if order is None:
            return "没有这张订单，请核对订单号。"
        if order["user_id"] != uid:
            # 越权第二闸：模型给的订单号 vs 注入的真实 uid 对不上 → 拒绝。
            # 注意话术里【不泄露】该订单是否存在/属于谁，防探测（Java 侧 403 同思路）
            return "无权查看该订单（订单不属于当前用户）。"
        # _MOCK_DETAILS.get(key, []) = map.getOrDefault(key, List.of())：没明细就给空列表，避免 KeyError
        return _format_detail(order, _MOCK_DETAILS.get(order_number, []))

    # ---------- 分支 B：真实调 Java，归属校验在 Java 侧完成 ----------
    # Java 端约定：404=订单不存在 / 403=不是本人的单，Python 按状态码区分话术（两道闸语义一致）
    try:
        resp = httpx.get(f"{c.JAVA_BASE_URL}/internal/orders/{order_number}",
                         params={"userId": uid}, **_JAVA_HTTP_OPTIONS)
        if resp.status_code == 404:
            return "没有这张订单，请核对订单号。"
        if resp.status_code == 403:
            return "无权查看该订单（订单不属于当前用户）。"
        resp.raise_for_status()
        body = resp.json()
        if body.get("code") != 1:
            return body.get("msg") or "订单查询失败，请稍后再试。"
        data = body["data"]
        order = {"number": data["order"]["number"], "status": data["order"]["status"],
                 "amount": data["order"]["amount"], "order_time": data["order"]["orderTime"]}
        return _format_detail(order, data.get("details") or [])
    except Exception as e:
        return f"订单服务暂时不可用（{type(e).__name__}），请稍后再试。"


# ==================== 工具 3：转人工 / 建工单 ====================
@tool
def create_ticket(category: str, content: str, order_number: str | None = None,
                  runtime: ToolRuntime[UserContext] = None) -> str:
    """用户要求转人工、投诉、退款协商或反馈问题时，创建一张售后工单。不要承诺退款结果，只负责登记。
    Args:
        category: 工单类别，如 退款/催单/投诉/配送/其他
        content: 用户诉求的简要描述（用客服口吻概括，不要原样堆叠语气词）
        order_number: 关联订单号，没有关联订单可不填
    """
    uid = runtime.context.user_id
    request_id = runtime.context.request_id
    if not request_id:
        return "缺少工单请求标识，无法安全创建工单；请重新发起请求。"
    payload = {"userId": uid, "category": category, "content": content,
               "orderNumber": order_number, "requestId": request_id}   # Java DTO 驼峰命名

    # ---------- 分支 A：mock，本地造工单号（不真正落库） ----------
    if c.MOCK_JAVA:
        # 纯 Mock 造号不落库；真实幂等性由 Java/MySQL 唯一约束保证。
        ticket_no = f"TK{int(time.time() * 1000)}"
        runtime.context.ticket_no = ticket_no
        return f"已为你创建人工工单 {ticket_no}（类别：{category}），客服会尽快与你联系。"

    # ---------- 分支 B：真实调 Java /internal/tickets，落库 customer_service_ticket 表 ----------
    previously_unknown = runtime.context.write_result_unknown
    runtime.context.write_result_unknown = True  # 发出写请求后，在收到明确结果前均视为未知
    try:
        resp = httpx.post(f"{c.JAVA_BASE_URL}/internal/tickets",
                          json=payload, **_JAVA_HTTP_OPTIONS)   # json= 自动序列化并设 Content-Type
        resp.raise_for_status()
        body = resp.json()
        if body.get("code") != 1:
            # 本次明确被拒绝，不覆盖此前同 ID 写入结果未知的事实。
            runtime.context.write_result_unknown = (
                previously_unknown or (body.get("data") or {}).get("outcome") == "unknown")
            return body.get("msg") or "工单创建失败，请稍后再试。"
        ticket_no = body["data"]["ticketNo"]   # 字典逐层取值 = JSON 反序列化后 getObject().getTicketNo()
        if not isinstance(ticket_no, str) or not ticket_no.strip():
            raise ValueError("missing ticket number")
        runtime.context.ticket_no = ticket_no
        runtime.context.write_result_unknown = False
        return f"已为你创建人工工单 {ticket_no}（类别：{category}），客服会尽快与你联系。"
    except httpx.TimeoutException:
        return "工单提交结果暂时无法确认。请勿重复创建；系统可用同一请求标识重试并取回原工单号。"
    except Exception as e:
        return f"工单服务暂时不可用（{type(e).__name__}），请稍后再试。"


# ==================== 工具 4：FAQ 知识库检索（RAG，阶段 8 新增） ====================
# 【与前三件工具的本质区别】前三件都查"用户自己的数据"（订单/工单），需注入 userId 防越权；
#   FAQ 是【公共知识库】，对所有用户一致，所以本工具不要 runtime —— 少一份耦合、多一份明确。
# 【为什么独立成工具而不是直接拼进 SYSTEM_PROMPT】30 条 FAQ 全塞进系统提示词，
#   既占 token 又让模型在每轮决策时被无关上下文稀释注意力；用工具按需召回，更省也更准。
@tool
def query_faq(question: str) -> str:
    """从 FAQ 知识库中检索与用户问题最匹配的常见问答。当用户问到退款规则、配送费、起送价、
    优惠券使用、支付方式、会员积分、订单状态含义等【通用规则】类问题时调用此工具，
    返回的答案必须按原文引用，不要改写金额、时长、阈值等数字。
    不要用此工具查询【当前用户】的具体订单（那是 query_orders 的职责）。
    Args:
        question: 用户问题原文（如"退款多久到账""配送费怎么算"），尽量保留原意不要改写
    """
    try:
        hits = faq_rag.search(question)   # top_k 默认走 config.RAG_TOP_K
    except Exception as e:
        # 模型没下完 / faq_data 缺失 / numpy 报错：兜底一句话，绝不抛穿 Agent
        return f"FAQ 知识库暂时不可用（{type(e).__name__}）；当前无法核实规则，请勿猜测金额或时限，可建议转人工。"
    if not hits:
        return "FAQ 知识库暂无相关条目；当前无法核实这项规则，请勿凭印象回答具体金额或时限。"
    # 拼成"序号 · Q/A"格式，让模型能逐条引用原文；不暴露 score 给模型，避免它死磕分数做决策
    lines = []
    for i, h in enumerate(hits, 1):
        lines.append(f"{i}. Q: {h['question']}\n   A: {h['answer']}")
    return "\n".join(lines)

def run(user_id: int, session_id: str, message: str, request_id: str | None = None,
        context: UserContext | None = None) -> tuple[str, list[str]]:
    """跑一轮对话。
    :param user_id:   真实登录用户 id（来自 Java 解析好的登录态，不是模型给的）
    :param session_id: 会话 id，同一个值 = 同一份历史 = 多轮记忆
    :param message:   用户这句话
    :param context:   HTTP 层传入的本次执行上下文；工具在其中记录写入结果，不参与历史记忆
    :return: (最终回复文本, 本轮实际调用过的工具名列表)  —— 工具名单用于前端展示/日志观测
    """
    result = _get_agent().invoke(
        {"messages": [{"role": "user", "content": message}]},   # 输入：本轮用户消息（历史由 checkpointer 自动拼）
        context=context if context is not None else UserContext(
            user_id=user_id, request_id=request_id or uuid.uuid4().hex),
        config={"configurable": {"thread_id": session_id}},     # 记忆的"抽屉号"：同 thread_id 共享历史
    )
    messages = result["messages"]
    # ⑤⑥ 走完后 messages 里是完整轨迹，形如：
    #   [HumanMessage(用户), AIMessage(带tool_calls), ToolMessage(工具结果),
    #    AIMessage(带tool_calls), ToolMessage(工具结果), ..., AIMessage(最终回复)]
    # checkpointer 会把历史轮次也放在 messages 中；只看最后一条 HumanMessage 之后的工具结果。
    # 否则第二轮会把第一轮的 query_orders 错报为本轮调用，污染前端展示和调用次数统计。
    last_human = max((i for i, m in enumerate(messages) if m.type == "human"), default=-1)
    tool_calls = [m.name for m in messages[last_human + 1:] if m.type == "tool"]
    reply = messages[-1].content                             # 最后一条 AIMessage 即最终回复
    return reply, tool_calls
class ChatResp(BaseModel):
    reply: str
    toolCalls: list[str]
    # completed=本轮处理已结束，不等于工单/退款业务成功；unknown=结果需保留 ID 核对。
    outcome: Literal["completed", "unknown"]


@app.post("/agent/chat")
def chat(req: ChatReq, x_internal_token: str | None = Header(default=None)):
    # 这里是 Java -> Python 的服务间入口。userId 由 Java 解析 JWT 后传入，
    # 因此必须先验证调用方确实是 Java 服务；否则攻击者能直接请求此接口并伪造 userId。
    # compare_digest 避免普通字符串比较在理论上泄露比较耗时差异。
    if not x_internal_token or not hmac.compare_digest(x_internal_token, c.INTERNAL_TOKEN):
        raise HTTPException(status_code=401, detail="invalid internal token")
    # 没配 key：接口不报 500，回一句可展示的兜底文案（与 Java 手写版同款"优雅降级"体验）
    if not c.DEEPSEEK_API_KEY:
        return ChatResp(reply="AI 服务未配置 DEEPSEEK_API_KEY，请在 python-agent/.env 中配置后重启。",
                        toolCalls=[], outcome="completed")
    context = UserContext(user_id=req.userId, request_id=req.requestId or uuid.uuid4().hex)
    try:
        # 核心一步：转手给 agent 层。门童不关心 ReAct 循环怎么转，只关心拿到 (reply, toolCalls)
        # 记忆键必须包含真实用户 id：不同用户即便巧合使用相同 sessionId，也不能共享上下文。
        memory_session_id = f"user-{req.userId}:{req.sessionId}"
        reply, tool_calls = agent_module.run(req.userId, memory_session_id, req.message,
                                            request_id=context.request_id, context=context)
    except Exception as e:
        traceback.print_exc()   # 栈打在服务端控制台（= 服务端日志），客户端只收到友好文案
        # 写入成功后模型生成失败，仍可以依据真实工单号确认结果。
        if context.ticket_no and not context.write_result_unknown:
            return ChatResp(reply=f"工单已登记，工单号 {context.ticket_no}。请等待商家核实，登记不代表退款完成。",
                            toolCalls=["create_ticket"], outcome="completed")
        return ChatResp(reply=f"AI 服务暂时开小差了（{type(e).__name__}），操作结果需核对，请保留请求 ID。",
                        toolCalls=[], outcome="unknown")
    if context.write_result_unknown:
        # 此时模型即使输出了“已创建”，也不能覆盖工具记录的未知状态。
        return ChatResp(reply="工单提交结果暂时无法确认。请保留请求 ID，先核对原工单结果再重试。",
                        toolCalls=tool_calls, outcome="unknown")
    if context.ticket_no:
        reply = f"工单已登记，工单号 {context.ticket_no}。请等待商家核实，登记不代表退款完成。"
    return ChatResp(reply=reply, toolCalls=tool_calls, outcome="completed")
    @GetMapping("/ticket-result")
    public Result<ServiceChatVO> ticketResult(@RequestParam String requestId, HttpServletRequest request) {
        Long userId = aiUserResolver.resolve(request);
        if (!requestId.matches("[A-Za-z0-9_-]{8,64}")) {
            return Result.error("requestId 格式不合法");
        }
        String ticketNo = internalApiService.findTicketNoByRequestId(userId, requestId);
        return Result.success(ServiceChatVO.builder()
                .reply(ticketNo == null
                        ? "暂未查到这次请求的工单，原请求可能仍在处理中；重试请保持原请求 ID。"
                        : "已核对原工单，工单号 " + ticketNo + "。本次没有重复创建，工单登记不代表退款完成。")
                .outcome(ticketNo == null ? "unknown" : "completed")
                .toolCalls(Collections.emptyList()).build());
    }
    @Override
    public String createTicket(TicketCreateDTO dto) {
        Long userId = dto.getUserId();
        if (userId == null || userId <= 0) {
            throw new TicketBusinessException("用户身份无效，无法登记工单。");
        }
        String orderNumber = normalizeOrderNumber(dto.getOrderNumber());
        // 已提交请求先恢复原结果；当前订单状态变化不应令原工单无法取回。
        CustomerServiceTicket previous = internalApiMapper.getTicketByRequestId(userId, dto.getRequestId());
        if (previous != null) {
            return replayTicket(previous, dto, orderNumber);
        }
        // 模型可以选择订单号，但 Java 必须独立校验；非空无效单号不能悄悄改成不关联订单。
        if (orderNumber != null) {
            Orders order = internalApiMapper.getByNumber(orderNumber);
            if (order == null || !Objects.equals(order.getUserId(), userId)) {
                // 统一不存在/非本人话术，避免经建单接口区分他人订单是否存在。
                throw new TicketBusinessException("未找到可关联的订单，请核对订单号。");
            }
        }
        // 一次用户发送动作只允许一张工单；同一 requestId 携不同内容属于冲突，不能静默复用。
        String ticketNo = "TK" + UUID.randomUUID().toString().replace("-", "").substring(0, 30);
        CustomerServiceTicket ticket = CustomerServiceTicket.builder()
                .ticketNo(ticketNo)
                .requestId(dto.getRequestId())
                .userId(dto.getUserId())
                .orderNumber(orderNumber)
                .category(dto.getCategory())
                .content(dto.getContent())
                .status(CustomerServiceTicket.PENDING)
                .createTime(LocalDateTime.now())
                .build();
        try {
            internalApiMapper.insertTicket(ticket);
            return ticketNo;
        } catch (DuplicateKeyException ex) {
            // 唯一约束是并发下的最终裁判：首请求可能已提交，但响应在网络中丢失。
            CustomerServiceTicket committed = internalApiMapper.getTicketByRequestId(
                    dto.getUserId(), dto.getRequestId());
            if (committed == null) {
                throw ex; // 极低概率的 ticket_no 碰撞等其他唯一键冲突，不能误报成功
            }
            return replayTicket(committed, dto, orderNumber);
        }
    }

    private String normalizeOrderNumber(String number) {
        return number == null || number.trim().isEmpty() ? null : number.trim();
    }

    private String replayTicket(CustomerServiceTicket previous, TicketCreateDTO dto, String orderNumber) {
        if (!Objects.equals(previous.getCategory(), dto.getCategory())
                || !Objects.equals(previous.getContent(), dto.getContent())
                || !Objects.equals(normalizeOrderNumber(previous.getOrderNumber()), orderNumber)) {
            throw new IllegalArgumentException("requestId 已用于另一条工单诉求");
        }
        return previous.getTicketNo();
    }
  async function run(item, isRetry) {
    if (busy) return;
    setPending(item); setBusy(true);
    if (!isRetry) add('user', item.message);
    const bubble = add('ai', '正在处理…');
    try {
      if (isRetry) {
        const receiptResponse = await fetch('/user/service/ticket-result?requestId=' + encodeURIComponent(item.requestId), {method:'GET'});
        const receipt = await receiptResponse.json();
        if (!receiptResponse.ok || receipt.code !== 1 || !receipt.data) throw new Error('原工单结果核对失败，已保留请求 ID');
        if (receipt.data.outcome === 'completed') {
          bubble.textContent = receipt.data.reply;
          setPending(null);
          status.textContent = '已取回原工单，本次未重复提交。';
          return;
        }
        if (receipt.data.outcome !== 'unknown') throw new Error('工单核对状态不完整');
      }
      const response = await fetch('/user/service/chat-python', {method:'POST', headers:{'Content-Type':'application/json'}, body:JSON.stringify(item)});
      const body = await response.json();
      if (!response.ok || body.code !== 1 || !body.data) throw new Error(body.msg || 'HTTP ' + response.status);
      bubble.textContent = body.data.reply || 'Agent 未返回文字。';
      if (Array.isArray(body.data.toolCalls) && body.data.toolCalls.length) { const trace = document.createElement('span'); trace.className = 'trace'; trace.textContent = '本轮工具：' + body.data.toolCalls.join(' → '); bubble.appendChild(trace); }
      if (body.data.outcome === 'completed') {
        setPending(null);
      } else {
        status.textContent = '处理结果未确认；已保留请求 ID，可先核对原工单。';
      }
    } catch (error) {
      bubble.textContent = '未收到明确结果：' + error.message + '。不要把超时当作操作失败；如需重试，请使用下方按钮复用相同请求 ID。';
      status.textContent = '上次结果未知，可使用“重试上一条”。';
    } finally { setBusy(false); }
