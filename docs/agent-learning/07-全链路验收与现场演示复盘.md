# 售后 Agent 全链路验收与现场演示复盘（2026-09-27）

## 先给结论

**已确认：本地演示链路可以从顾客提问走到商家工单状态处理。** 本次在真实浏览器中依次完成查单、追问明细、创建一张明确标记为“联调测试”的工单、商家登录、查看同一工单、从待处理推进到处理中和已完结；MySQL 中同一工单号只有一行。`已完结` 只是工单状态，**没有执行补送、退款或向顾客发送处理结果**。

**不能据此声称“整个项目/生产能力全面完成”。** 这是一条本地演示样本，不覆盖真实微信身份、支付、真机、商家旧页面所有写操作、并发压力、真实丢包、跨进程持久记忆或生产部署安全。自动评测的 Mock 成绩也不能替代这条真实链路。

## 你亲自演示时照这个顺序走

前提：本机 Docker 四个服务已启动；旧后台适配器监听 `127.0.0.1:8081`。当前演示库有订单 `20260917123000002`；如果你清空或换了数据库，应先查新订单号，不要照抄旧号码。聊天会产生模型费用，建工单会写入本地数据库。商家演示账号写在 `docker/seed/02-sample-data.sql`，只限本机演示环境。

1. 顾客页打开 `http://127.0.0.1:8080/service-agent.html`，点“新会话”。说：“我的订单有哪些？”预期页面出现真实订单号，工具轨迹是 `query_orders`。
2. 同一会话说：“刚才那单有什么菜？”预期答复来自 `query_order_detail`，能看到菜名。这里要解释：同一个 `sessionId` 让模型看到之前的对话，而订单事实仍重新从 Java 查；不是靠记忆编菜名。
3. 明确说：“【联调测试，非真实售后】订单 20260917123000002 少送菜，请创建人工工单，内容注明联调测试，不要承诺退款。”预期工具是 `create_ticket`，记录页面显示的工单号。**模型有自主决策，工具轨迹可能变化；不能把预期写成每次必然。** 若没有建单，先看工具轨迹与回复，不要盲目重复点击。
4. 商家页打开 `http://127.0.0.1:8081/` 登录，点击“售后工单”，按刚才工单号核对用户、订单、内容和状态。点击“开始处理”→“标记完结”。讲清两个确认弹窗、状态只能 `1→2→3`，以及“完结≠退款”。
5. 可选再问：“你们支持 Apple Pay 吗？”预期调用 `query_faq`，回答应承认证据不足，而不是凭常识承诺支持。

面对面时用这条链路讲职责，而不是只背框架名称：

```text
顾客页面 → Java /user/service/chat-python（解析用户身份）
         → Python /agent/chat（验证 Java 的内部令牌）
         → Agent 选择工具、从会话 checkpointer 读取历史
         → Python 工具带运行时 userId 回调 Java /internal/**
         → Java 查订单或写工单到 MySQL → Agent 组织回复
         → 商家 JWT 页面读 /admin/tickets、推进工单状态
```

`query_orders`、`query_order_detail`、`create_ticket` 是**本轮实际工具**；`toolCalls` 不是“所有可用工具列表”。订单号/工单号是可核对事实；“会尽快联系”是系统提示/工具文案，不是已验证的人工响应 SLA。

## 失败时如何归因，而不是说“模型不稳定”

| 现场症状 | 先看哪一层 | 能确认什么 / 不能直接推断什么 |
| --- | --- | --- |
| 页面 `Failed to fetch` | 浏览器 Network 是否发出 POST、Java 8080 是否可达、代理/跨域 | 未收到结果时可能已写库；不能直接断言建单失败后换 ID 重试 |
| Java 返回兜底“Python 不可用” | Python `/health`、容器日志、Java→Python 令牌及 60 秒超时 | HTTP 200 的兜底文案也不代表业务成功；需查 Python 日志和工单表 |
| 查单没有结果或菜名不对 | `toolCalls`、Java `/internal/orders` 与数据库订单归属/明细 | 模型没调工具是路由问题；工具回了错数据是 Java/数据问题；不要混归因 |
| 第二轮把第一轮的工具也算进去 | 看本轮最后一条 HumanMessage 后的 ToolMessage | 这是轨迹统计错误，不一定是重复查询；当前实现已针对该问题回归 |
| Agent 说建单成功，商家页没有 | 核对工单号、商家筛选/刷新、MySQL 精确查询、Java 返回和日志 | 不要只凭自然语言回复断定落库；以唯一工单号及数据库记录为准 |
| 同一诉求出现两张工单 | 比较 `userId + requestId`、外层是否重用了同一请求 ID、DB 唯一索引 | 目前仅保证同一 ID 的写入幂等；换 ID 重试仍可能重复 |
| FAQ 答得很肯定却无证据 | 查 `query_faq` 返回原文、`faq_grounded.json`、实际前后端能力 | 向量库有文字不等于功能已上线；支付/退款需实际部署验收 |
| 商家页空白/401 | 先确认登录 cookie/JWT、适配器 8081 与 Java 8080 | 旧编译包靠本地适配，不能把它当成可直接部署的新前端 |

### 重点面试题：超时歧义

假设 Java 已把工单写入 MySQL，Python 或顾客浏览器在收到响应前超时。此时“没收到成功”既可能是没写入，也可能是写入成功、响应丢了。当前页面会保留这次请求的 `requestId` 供重试，Java 数据库对 `(user_id, request_id)` 做唯一约束；同一 ID 且相同内容的重试返回原工单号，内容变了会冲突。但**本次没有注入真实丢包/超时**，所以这是代码与契约层面的设计，不是已完成故障注入验收。若用户刷新后另发一条新消息或换 ID，该保障不自动跨请求生效。

## 学习验收：先自己说，再看答案

1. 为什么第二句“刚才那单”能找到订单，而菜名仍要调用工具？
2. `requestId`、`sessionId`、`userId` 各解决什么问题？谁能由模型修改？
3. 页面超时但数据库已有工单时，为什么不能生成新 ID 立即重试？
4. 为什么商家把工单标为已完结，不等于客户已收到退款？
5. Agent 回答 Apple Pay “没有证据”，为什么比直接回答“不支持”更严谨？

参考要点：`sessionId` 找会话历史；订单事实由 Java 工具查。`requestId` 是同一次写入动作的幂等键，`userId` 来自 Java 可信身份并注入工具运行时，模型只决定允许暴露的工具参数。超时结果未知，换 ID 会绕开唯一约束。工单状态与资金动作是不同业务对象。缺少支付实现/部署证据，只能说无法确认，不能把“未证实”偷换为“确定不支持”。
