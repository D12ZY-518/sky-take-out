# FAQ 与后端能力对账：别把检索命中当成业务事实

## 结论与证据边界

旧版 [`faq_data.json`](../../python-agent/faq_data.json) 的 30 条是**演示文本**，不是已批准的运营政策。按当前仓库静态代码核对，里面有大量无法证实的金额、时限、权益和页面入口，例如“Apple Pay”“会员积分兑换”“退款 1–3 个工作日”。**未找到实现**只说明本仓库不能支持这项承诺，不等于真实商家一定没有该政策；这里没有外部产品政策的核验权限。

因此运行时改用 [`faq_grounded.json`](../../python-agent/faq_grounded.json) 的 13 条保守问答：有代码依据的只说后端能做什么；没有依据的明确说无法核实，不补编数字。Chroma 使用独立 collection `faq_grounded_v3`，旧索引留在磁盘但不再服务，避免缓存继续召回未核实文本。旧 30 条保留作 Bad Case/对账样本，不作为当前用户答复依据。v3 还明确：订单工具没有配送费拆分和优惠券字段；代码里有微信支付对接，也不能证明真实支付渠道当前可用。

## 逐组对账

| 旧 FAQ ID | 原说法类型 | 当前仓库证据 | 判定与处理 |
| --- | --- | --- | --- |
| 1–3、16 | 固定退款时限、独立申请/部分退款/进度查询 | `OrderServiceImpl.userCancelById` 与商家拒单路径会调用微信退款；未找到独立申请、部分退款或到账 SLA | 部分能力有代码，时限与流程不可证实；改为保守答复 |
| 4、20–23 | 投诉入口、上传照片、补送/赔偿、24 小时受理 | `InternalApiController` 只能建工单，四个 Agent 工具无上传或追加 | “可登记工单”有依据；照片、赔偿和 SLA 不可承诺 |
| 5–10 | 配送时间、配送费、夜间费、免配送费、起送价 | `OrderServiceImpl.submitOrder` 未见费用/起送规则；仓库无会员配送权益逻辑 | 不可证实固定数值；运行时不再给出这些数字 |
| 11–14 | 领券、叠加、有效期、新人礼包 | 当前 Java 控制器/服务未找到券的领取或核销流程 | 不可证实；不能回答具体券规则 |
| 15、17–19 | 取消、改地址、再来一单、状态与配送位置 | `OrderController` 有取消、再来一单；`OrderServiceImpl` 只允许待付款/待接单取消；`Orders` 定义状态；无已下单改地址和实时位置证据 | 保留可证实的取消/状态/再来一单后端事实，去掉页面与实时位置承诺 |
| 24–26 | 修改手机号、地址管理、注销 | `AddressBookController` 有地址增删改查与默认地址；其他流程未找到 | 只保留地址后端能力，不承诺页面入口或注销流程 |
| 27–28 | 支付宝/银行卡/Apple Pay/余额/货到付款、15 分钟自动取消 | `OrderServiceImpl.payment` 有微信对接代码；实体注释提支付宝不等于实现；未找到这些其他支付流程或 15 分钟取消任务 | 只说可核实的代码路径，不承诺微信支付当前可用；其余不可承诺 |
| 29–30 | 会员等级、积分兑换、到期 | 当前 Java 业务模块未找到对应服务/控制器 | 不可证实；运行时明确提示无法核实 |

“订单状态”“地址 CRUD”等也只证明后端代码存在，**未验证前端按钮、支付渠道、部署配置和真实运营承诺**。对外发布前应由业务负责人逐条确认规则，并给每条 FAQ 增加来源、审核人、生效/失效时间；这是建议，当前尚未实现审批流。

## 你可以复现

1. 从项目根目录运行 `rg -n 'Apple Pay|会员积分|1-3 个工作日' python-agent/faq_data.json`，看旧题库的未核实承诺。
2. 运行 `rg -n 'refund|weChatPayUtil|repetition|reminder' sky-server/src/main/java/com/sky/service/impl/OrderServiceImpl.java`，再看取消、拒单、再来一单、催单的真实条件。别把“没搜到”单独当成证明，结合控制器/服务与业务方确认。
3. 运行 `docker compose exec -T python-agent python -c "import config,faq_rag; print(config.FAQ_DATA_PATH,len(faq_rag._load_faqs()))"`；当前应是 `faq_grounded.json 13`。
4. 运行 `docker compose exec -T python-agent python -c "import faq_rag; print([(x['question'],round(x['score'],3)) for x in faq_rag.search('支持 Apple Pay 吗',top_k=2)])"`；应命中“支持哪些支付方式”的保守条目。检索命中不等于最终回复正确，仍需人工看模型是否改写为“支持 Apple Pay”或承诺工具没有的查询能力。

## 面试时怎么讲

“我一开始把 30 条演示 FAQ 直接做向量检索，模型能引用到答案，但我后来发现检索正确不代表业务真实。比如旧题库写支持 Apple Pay，后端实际只找到微信支付实现。我逐组对账后，保留旧题库作审计样本，换成 13 条有依据或明确未知的保守问答，并换了 Chroma collection，防止旧索引继续召回错误文本。现在我能证明的是**减少了已知错误事实源**，还不能证明真实运营政策已审核，也不能保证模型绝不误答；上线前需要业务审核和更多答复评测。”

闭卷追问：如果向量检索召回了正确来源，但模型把“不能承诺 1–3 天”说成“一定 3 天到账”，这是知识库错误、召回错误还是生成错误？你会保留哪些证据区分？
