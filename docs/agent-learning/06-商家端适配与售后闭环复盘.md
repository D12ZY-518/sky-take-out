# 06｜商家端适配与售后闭环复盘

## 先用自己的话讲（面试 60 秒）

旧商家端是瑞吉外卖的编译包，不是当前 Java 项目的源码前端。我保留原件，用只监听本机的 Node 适配器把 `/api/*` 转发到 Java `/admin/*`。联调发现三个具体不兼容点：Java 的时间字段是数组、旧包的 WebSocket 地址指向错误端口、管理端缺少订单详情接口。前两项在本地适配器转换，后一项在 Java 增加受管理员 JWT 保护的 `/admin/order/details/{id}`；用户端详情仍按当前用户 ID 校验归属。旧包把配送费写死为 6 元，但后端没有独立配送费字段，因此演示适配器改为展示数据库订单总额，并注明配送费未单独记录。

Python Agent 创建工单原先只写进 MySQL。为了让商家能接手，新增管理端工单查询和状态接口，以及侧栏的独立工单页。管理端 JWT 保护读取与更新；状态按 `1 待处理 → 2 处理中 → 3 已完结` 推进，SQL 更新带原状态条件，避免并发覆盖。重复提交相同目标状态直接返回成功；若另一个人已经推进到其他状态，则提示刷新。工单完结不是退款成功，当前没有退款执行接口。

## 你要能画出的链路

```text
顾客小程序 → Java /user/service/chat-python → Python Agent
  → create_ticket 工具 → Java /internal/tickets → MySQL 工单表
                                               ↓
商家旧后台 → 本地适配器 /api/tickets → Java /admin/tickets → 查询/处理工单
```

注意两段身份不同：Agent 内部写工单用 `X-Internal-Token` 与上下文中的用户 ID；商家读和处理工单用管理员 JWT。不能把服务间令牌发到浏览器，也不能把“能打开静态工单页”当成“能读取工单”——无管理员 JWT 时 API 返回 401。

## 关键代码与语法

- [管理端工单控制器](../../sky-server/src/main/java/com/sky/controller/admin/TicketController.java)：`@RequestMapping("/admin/tickets")` 给类中方法统一加路径前缀；`@RequestParam(defaultValue="20")` 提供分页默认值；`@RequestBody` 把 JSON 请求体解析为 Java 对象。
- [状态业务服务](../../sky-server/src/main/java/com/sky/service/impl/AdminTicketServiceImpl.java)：`@Transactional` 让同一次状态推进中的数据库操作处于事务内；`nextStatus.equals(ticket.getStatus())` 处理同目标重试；`update ... where id=? and status=?` 是数据库层的条件更新（类似 compare-and-set），不能只靠 Java 中先查再判断防并发。
- [管理端订单详情](../../sky-server/src/main/java/com/sky/service/impl/OrderServiceImpl.java)：管理端可按订单 ID 读详情，用户端则必须按 `订单 ID + 当前用户 ID` 查询，二者不能互换。
- [本地适配器](../../scripts/legacy_admin_demo.js)：只修旧编译包格式差异，不修改原始课程资料；旧包升级后必须重跑适配脚本测试和页面验收。

`List<CustomerServiceTicket>` 是一组工单；`PageHelper.startPage(page, pageSize)` 在紧随其后的 Mapper 查询上加入分页；`PageResult(total, rows)` 同时返回总条数和当前页。这里的 `Integer` 可以为 `null`，代表“不按状态筛选”，所以参数校验要先判断 `null`。
